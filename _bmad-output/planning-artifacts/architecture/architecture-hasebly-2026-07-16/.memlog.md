- (decision) Paradigm: client + thin stateless backend proxy (Option B over pure-client Option A). Binds: client never holds the OCR/vision-LLM API key. Prevents: an extractable on-device API key and a future unit re-adding server logic directly into the client.
- (decision) Stack: React Native via Expo (SDK 56, React Native 0.86 current as of mid-2026, web-verified) for the single iOS+Android client codebase. User has existing JS/TS familiarity - picked over Flutter on that basis, not technical merit.
- (decision) OCR approach: vision-capable multimodal LLM API (structured JSON extraction) called from the backend proxy, not a dedicated OCR service (Google Vision/Azure Document Intelligence) + custom parsing. This is the exact approach the 22-receipt spike already validated - avoids re-deriving structured extraction from raw OCR text/boxes.
- (decision) Backend owns no data and has no database in v1 - stateless request/response proxy only (receives receipt image, calls vision-LLM API, returns structured JSON, persists nothing). Binds: v1 backend. Prevents: a future unit quietly adding server-side storage that contradicts PRD SS6.2's explicit deferral of accounts/history to post-validation.
