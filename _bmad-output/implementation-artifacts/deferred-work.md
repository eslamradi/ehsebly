## Deferred from: code review of 1-5-assign-items-to-people-including-shared-items (2026-07-21)

- ~~**[HIGH — flagged for likely dedicated fix, not just tracking] `TaxServiceScreen`'s draft-commit logic has multiple silent-data-loss/no-error-feedback bugs**~~ — **RESOLVED (2026-07-22).** [client/app/screens/TaxServiceScreen.tsx] — pre-existing from Story 1.3 (already marked `done`), surfaced during Story 1.5's review by two independent reviewers with precise code citations, not introduced by Story 1.5:
  1. `commitTaxRateDraft`/`commitServiceRateDraft` both build their `setTaxService({...taxService, ...})` call from the same render-time `taxService` closure variable rather than the latest committed state. Calling both synchronously (as `handleBack` does) means the second call overwrites the first: editing both tax rate and service rate, then pressing Back, silently reverts the first edit even though both were individually valid.
  2. `handleTaxToggle`/`handleServiceToggle` fall back to the last-committed rate via `resolveTaxRate`/`resolveServiceRate` when the pending draft is unparseable, but never call `setTaxRateError(true)`/`setServiceRateError(true)` the way the blur path does — an invalid in-progress edit vanishes on toggle with zero visible feedback.
  3. Neither toggle handler clears a previously-set error flag, so a stale "Couldn't read that rate — kept the previous value." message can keep rendering after the condition that caused it is gone.
  4. `handleBack` calls `navigation.navigate(...)` synchronously right after the commit functions, so even when a commit *does* set an error flag, the screen navigates away in the same tick — the error text can never actually be seen by the fronter.
  Net effect: a fronter can type a corrected tax/service rate, have it silently discarded or overwritten, and never know it happened — directly undermines trust in the one number (tax/service rate) the entire split's correctness depends on. **Fix:** `session.tsx`'s `setTaxService` now accepts a React-style updater function in addition to a plain value; `commitTaxRateDraft`/`commitServiceRateDraft` use it so two commits queued in the same handler compose against true latest state instead of the same stale closure (fixes #1). Both toggle handlers now explicitly set/clear the error flag based on the current draft's validity (fixes #2, #3). `handleBack` now only navigates once both commits report success, so an invalid draft keeps the fronter on-screen to see the error (fixes #4). Typechecked clean; no automated test coverage exists for this screen yet (consistent with v1's stated test-infra deferral) — worth exercising by hand before the next real dinner.
- No stable person ID — people identified purely by array index [client/app/domain/session.tsx] — already acknowledged in Story 1.5's own Dev Notes as safe only while no reorder/remove feature exists; revisit if one is ever added.
- No way to remove or rename a person once added to the roster [client/app/domain/session.tsx, client/app/screens/ItemAssignmentScreen.tsx] — real usability gap (a typo'd name is permanent for the session), but not required by any AC/FR; candidate for a future story if it surfaces as real friction during the 10-dinner test.
- No duplicate-name protection when adding a person [client/app/screens/ItemAssignmentScreen.tsx] — two people with identical names produce indistinguishable chips; real but out of this story's stated minimal-validation scope (reject empty/whitespace-only only).
- `calculatePersonSubtotals` has no bounds-check on `personIndex` [client/app/domain/assignment.ts] — currently unreachable since no person-removal path exists yet; would silently corrupt totals if one is ever added without also updating this function.
- No `KeyboardAvoidingView` on scroll screens with text inputs [client/app/screens/ItemAssignmentScreen.tsx, client/app/screens/TaxServiceScreen.tsx] — pre-existing pattern across every screen since Story 1.2, not specific to this story; keyboard can obscure lower inputs on some devices.
